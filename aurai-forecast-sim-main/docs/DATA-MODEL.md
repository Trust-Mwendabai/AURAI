# Data Model

The MySQL/MariaDB schema the PHP API runs against. The authoritative source is
[`/database/schema.sql`](../database/schema.sql); this page explains what each
table is for.

Primary keys are `CHAR(36)` UUIDv4 strings generated by PHP before each insert
(`uuid4()` in `api/lib/helpers.php`), because MySQL cannot portably default a
column to a UUID.

`login_attempts` stands alone — it is keyed by a hash rather than a user id, so
it has no foreign key.

## Tables

### `users`
Login credentials. Passwords are stored as a `password_hash()` digest, never in
any recoverable form.

| Column | Type | Notes |
|---|---|---|
| `id` | char(36), PK | app-generated UUIDv4 |
| `email` | varchar(255), unique | |
| `password_hash` | varchar(255) | bcrypt/argon2 via `password_hash()` |
| `email_verified_at` | datetime, nullable | reserved; nothing sets it today |
| `remember_token` | varchar(100), nullable | reserved; unused |
| `created_at` / `updated_at` | datetime | |

An `AFTER INSERT` trigger creates the matching `profiles` and `user_settings`
rows, so registration cannot forget to.

### `profiles`
Display data, kept separate from credentials.

| Column | Type | Notes |
|---|---|---|
| `id` | char(36), PK/FK → `users.id` | cascade delete |
| `name` | varchar(255), nullable | set at registration |
| `email` | varchar(255), nullable | mirrored from `users.email` |
| `avatar_url` | varchar(500), nullable | |
| `plan` | varchar(50), default `'free'` | display only; there is no billing |
| `preferences` | json, default `{}` | free-form; distinct from `user_settings.prefs` |
| `created_at` / `updated_at` | datetime | |

### `user_settings`
Per-user app preferences, written by the Settings page via `/settings`.

| Column | Type | Notes |
|---|---|---|
| `user_id` | char(36), PK/FK | cascade delete |
| `prefs` | json, default `{}` | `systemName`, `companyName`, `glassIntensity`, `forecastHorizon`, `forecastPeriod` |
| `updated_at` | datetime | |

These drive the sidebar name, the `--glass-blur` CSS variable, and the
Predictions wizard's defaults.

### `sessions`
Server-side bearer-token store — one row per active login.

| Column | Type | Notes |
|---|---|---|
| `id` | char(36), PK | |
| `user_id` | char(36), FK | cascade delete |
| `token_hash` | varchar(255), unique | SHA-256 of the token; the token itself is never stored |
| `ip_address` / `user_agent` | varchar, nullable | recorded at sign-in |
| `last_used_at` | datetime | bumped on each authenticated request |
| `expires_at` | datetime | 30 days out; expired rows are rejected and pruned on login |

### `password_reset_tokens`
Backs the forgot-password flow. One row per email, single-use.

| Column | Type | Notes |
|---|---|---|
| `email` | varchar(255), PK | one outstanding token per address |
| `token_hash` | varchar(255) | SHA-256; compared with `hash_equals` |
| `expires_at` | datetime | one hour |

### `login_attempts`
Rate-limits password guessing. Written only by the login endpoint.

| Column | Type | Notes |
|---|---|---|
| `id` | char(64), PK | SHA-256 of the email + client IP, so neither is stored in the clear |
| `attempts` | int | consecutive failures; cleared by a successful sign-in |
| `last_attempt_at` | datetime | the lockout window is measured from here |

After 8 failures within 15 minutes the endpoint returns 429. Counting per email
**and** IP means an attacker cannot lock someone out of their own account.

### `datasets`
An imported dataset. Rows are parsed client-side from CSV/JSON and stored
**inline as JSON** rather than as an uploaded file.

| Column | Type | Notes |
|---|---|---|
| `id` | char(36), PK | |
| `user_id` | char(36), FK | cascade delete |
| `name` | varchar(255) | the imported filename |
| `rows` | json, default `[]` | the parsed table, an array of row objects |
| `meta` | json, default `{}` | holds `headers`, the column order |
| `storage_path` | varchar(500), nullable | reserved for a real upload flow; unused |
| `created_at` / `updated_at` | datetime | `updated_at` also invalidates a trained model |

Index: `(user_id, created_at DESC)`.

`rows` can be large, so **`GET /datasets` deliberately omits it** and returns
`JSON_LENGTH(rows)` as `row_count` instead. Fetch a single dataset by id to get
its rows.

### `predictions`
The result of a forecast run.

| Column | Type | Notes |
|---|---|---|
| `id` | char(36), PK | |
| `user_id` | char(36), FK | cascade delete |
| `dataset_id` | char(36), FK → `datasets.id`, nullable | `SET NULL` if the dataset is deleted |
| `name` | varchar(255) | label shown in history |
| `target` | varchar(255), nullable | the column forecast |
| `horizon` | int, nullable | periods projected forward |
| `period` | varchar(50), nullable | Hourly … Yearly; maps to a pandas frequency |
| `algorithm` | varchar(100), nullable | label for the UI; Prophet is the only implemented model |
| `model_name` | varchar(255), nullable | the saved `.pkl` in `backend/Python/models` that produced this run |
| `accuracy` | decimal(5,2), nullable | reported by the forecasting service |
| `forecast` | json, default `[]` | `{ i, label, value, low, high }` points |
| `created_at` | datetime | compared against `datasets.updated_at` to decide whether the model is still valid |

Index: `(user_id, created_at DESC)`.

### `reports`
A rich-text report, edited in-browser and autosaved.

| Column | Type | Notes |
|---|---|---|
| `id` | char(36), PK | |
| `user_id` | char(36), FK | cascade delete |
| `title` | varchar(255), default `'Untitled report'` | |
| `body` | longtext | HTML from the editor — treat as untrusted when rendering elsewhere |
| `updated_at` / `created_at` | datetime | |

Index: `(user_id, updated_at DESC)`.

### `conversations` / `messages`
Chat threads for the Aurai assistant. Replies come from the `/assistant`
endpoint, which answers from SQL over the user's own rows — these tables just
persist the conversation.

`conversations`:

| Column | Type | Notes |
|---|---|---|
| `id` | char(36), PK | |
| `user_id` | char(36), FK | cascade delete |
| `title` | varchar(255), default `'New chat'` | |
| `updated_at` / `created_at` | datetime | `updated_at` bumped whenever a message is added |

`messages`:

| Column | Type | Notes |
|---|---|---|
| `id` | char(36), PK | |
| `seq` | bigint, AUTO_INCREMENT, unique | **ordering key** — see below |
| `conversation_id` | char(36), FK | cascade delete |
| `user_id` | char(36), FK | cascade delete |
| `role` | varchar(20) | `user` \| `assistant` \| `system`, enforced by a CHECK constraint |
| `content` | longtext | |
| `created_at` | datetime | second-precision only |

Messages are ordered by `seq`, not `created_at`: a question and an instant
answer share a timestamp, so sorting by time returns them in arbitrary order.

## Access control

MySQL has no row-level security, so **authorization is enforced entirely in
PHP**. Every `SELECT`/`UPDATE`/`DELETE` carries `AND user_id = :uid`, every
`INSERT` takes `user_id` from the session rather than the request body, and
`messages` are scoped through a join on their owning `conversations` row.

There is no database-level safety net. A query that forgets the filter returns
other users' rows — which is why the filtering is centralized per table in
`api/resources.php`. See [AUTHENTICATION.md](./AUTHENTICATION.md).
